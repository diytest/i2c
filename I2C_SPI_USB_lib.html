I2C SPI 1-Wire USB Adapter Software

USB Drivers

To connect to USB, the adapter uses the CP2102N USB bridge chip manufactured by Silicon Labs. The company offers the latest driver versions on its website.
VCP Drivers (Virtual COM-port) for various operating systems (Windows, WinCE, Mac, Linux) allow a computer, smartphone, or controller with a USB host to communicate with the adapter via a virtual COM port using the appropriate application.
USBxpress Direct Access Drivers are available for devices running Windows and WinCE operating systems.

For Windows, you can use archives containing Direct Access Drivers and Virtual COM Port Drivers.

The operating mode of the CP2102 USB bridge chip - either via a virtual COM port or with direct access - is determined by the USB PID (Product ID) parameter value written into this chip.
PID=0xEA61 - the adapter is shipped with this parameter value; its operation is supported under Windows and WinCE; the chip operates in the direct access mode to the USB bridge functions; a Direct Access Driver must be installed on the host device.
PID=0xEA60 - the application accesses the USB bridge chip as a Virtual COM Port; a VCP driver must be installed on the host device to which the USB bridge is connected; this mode is required for the adapter to work under Linux and Mac operating systems, as only VCP drivers are available for them. This mode is also supported under Windows and WinCE - a developer can use it if they prefer working with a virtual COM port over direct access to the USB bridge functions.

To change the USB parameter values (VID, PID, Product String, Serial Number,...) in the CP2102N USB bridge chip, the manufacturer offers Simplicity Studio.
As part of the I2C SPI 1-Wire USB adapter the IC CP2102N is shipped with PID=0xEA61.
If there is need to change CP2102N' PID to 0xEA60, you should first read the parameters already written during the manufacturing of the adapter (the "Import From Device" button), then change the PID to 0xEA60 and press the "Program To Device" button to save the changes.
Attention: loading the default parameters offered by Simplicity Studio into the CP2102N chip is unacceptable: the adapter will stop working.
To restore the adapter's functionality, you will need to enter the correct parameters.

For the operating system and the applications running within it, including Simplicity Studio, to detect your device, a driver with the VID, PID, and Product String parameters matching those written in the USB bridge chip you are connecting must already be installed on the computer.
If you have changed the VID, PID, or Product String parameters in these applications, and drivers with the new values of these parameters have not yet been installed, the operating system, and consequently, these applications, will not detect your device after the changes are applied.

Note:
  • Windows 10 strictly verifies devices for compliance with VID, PID, and Product String — they must be registered by the manufacturer, and modifying them requires a registration procedure at usb.org. Unregistered devices are blocked, and the procedure to unblock them in Windows 10 requires rather troublesome modifications. For the CP2102 chip, these parameters must be as follows: VID=0x10C4; PID=0xEA60 or PID=0xEA61
  • Windows 7 allowed devices to work with unregistered parameter values but required a specific procedure to permit the operation of such devices.
  • Windows Vista, XP, and 98 allowed these parameters to be changed arbitrarily. It was possible to connect multiple devices with CP2102 USB bridges, where, for example, the first device with such a bridge could be assigned PID=0xEA01, and the second PID=0xEA02. Of course, there was a chance that with such arbitrary usage, someone else might register their device with the VID=0x10C4 and PID=0xEA01 values you used, and your customer might purchase that device and attempt to use it alongside yours.

 Adapter Bootloader with ATmega8 and megaAVR 0-series Microcontrollers

In adapters with ATmega8 microcontrollers and megaAVR 0-series microcontrollers, the firmware contains not only the program for working with I2C, SPI, and 1-Wire interfaces, but also a bootloader program.
In adapters with STM8S003 microcontrollers, there is no bootloader program — these microcontrollers lack hardware support for a boot sector.

In ATmega8 and megaAVR 0-series microcontrollers, a boot area and an application area can be allocated in the program memory, which requires a programmer.
The application area hosts the microcontroller's working program — in the adapter's microcontroller, this is the program that ensures operation with I2C, SPI, and 1-Wire interfaces, as well as communication with a computer via USB.
The boot area hosts a program that allows loading updated firmware into the application area of the microcontroller's program memory without a programmer.

In the memory of the adapter's ATmega8 and megaAVR 0-series microcontrollers, the bootloader program and the universal program are already flashed. In the STM8S003 memory, only the universal program is flashed.

During a standard USB connection, the adapter's microcontroller runs the working program.
To switch to boot mode on a disconnected microcontroller, you need to short the "O" and "_|_" pins and, keeping them shorted, connect the adapter to USB.
The supplied working program of the microcontroller includes a command to switch from the working program to boot mode without shorting the pins.
For a working program developed by you to provide a software transition to boot mode, it must support the same command, and the microcontroller must use a baud rate of 500,000 baud. A baud rate of 500,000 baud is used in all supplied programs, including the Bootloader computer application. 
Компьютерное приложение Bootloader обеспечивает загрузку обновлённой прошивки, которая должна храниться в формате hex.  <Place links>

When the microcontroller is connected to USB, pressing the "MCU->to Bootloader" button switches the microcontroller (MCU) to boot mode.
Open the updated firmware file (the "Open firmware file *.hex" button), then press the "Write firmware to MCU" button.
As the firmware is loaded, the status panel displays the current number of the program page already written into the microcontroller's memory.
Pressing the "MCU->to program" button switches the microcontroller to program execution mode and disconnects the Bootloader application — you can run an application to control the adapter while keeping the Bootloader application open. To re-flash the firmware, you need to disconnect or close the adapter control application, and press the "MCU->to BootLoader" button in the Bootloader application. This is convenient when working on software development and testing each updated firmware version.

It is also possible to load updated firmware using a programmer — it can be connected to the SPI interface pins of the adapter:
Programmer pin:    _|_    +3.3V    MISO    MOSI    SCK    RST
Adapter pin:                _|_    V            O            I            C        MCU/pin 29 (connected to R=10k and a capacitor near pin 1 of the MCU, marked on the board with a checkmark — it is more convenient to solder the wire to the R and C pads)

When flashing via a programmer, a full erase of the microcontroller's memory is performed, including the bootloader area, and the bootloader program for the microcontroller is not provided. This means that after using a programmer, you will not be able to use our bootloader in the adapter.                 

 Adapter: Microcontroller Program

The microcontroller of the I2C SPI 1-Wire USB adapter (hereinafter MCU) recognizes and executes commands received via USB. Based on these commands, the MCU controls the devices connected to the adapter, reads data coming from them, and transmits it via USB to the computer.

MCU Transmission Parameters:

  • Information is transmitted in 8-bit words accompanied by service bits;
  • Baud rate is 500,000 baud; 
  • 1 stop bit; 
  • Parity bit — Odd.
The same parameters must be set in the computer application under whose control the adapter operates.

Computer Commands and MCU Responses.

The command byte is transmitted first, and the control record byte (CR) is transmitted last.
All values in commands and responses are single-byte, which includes device addresses, register addresses, requested data sizes, and register contents.
Note. All commands listed below are sent by the computer to the adapter.
The adapter processes the commands and sends them to the devices connected to the adapter in a converted form.
Device responses are also sent by the adapter to the computer in a processed form.
The communication format between the adapter and the devices connected to it is not covered here.

Connection Test and Bootloader Operations Commands.

These four commands are executed both with devices connected to the adapter and without them.

Connection Test with MCU Running the Working Program.

Command:
0x10 B[0] ... B[n-1] CR — up to a dozen arbitrary bytes B[0] ... B[n-1] can be placed between the 0x10 command byte and the control record; their transmission is optional. It is sufficient to transmit just the command byte and the control record: 0x10 0x10.
Response:
0x10 B[0] ... B[n-1] CR — the MCU response repeats the received sequence (command echo).
The control record CR is defined as the low byte of the sum of all previous bytes of the command:
CR = LowByteOf ( 0x10 + B[0] + ... + B[n-1] ).
An example of CR calculation is provided in the next section.

Switching to the MCU Bootloader Program from the Working Program.

0xBB 0xBB — command to switch the MCU to the bootloader. This command is executed by the MCU working program.
No response to this command is provided.

Connection Test with MCU Running the Bootloader Program.

0xB7 0xB7 — command executed by the bootloader. The bootloader does not respond to the 0x10 command described above.
0xB7 B[0] B[1] B[2] CR — the MCU response allows confirming the transition to the bootloader. Bytes B[0], B[1], B[2], and CR are calculated and transmitted by the bootloader.

Returning the MCU to the Working Program from the Bootloader Program.

0xBA 0xBA — command executed by the bootloader. No response to this command is provided.
To verify that the MCU has switched to the working program, execute the 0x10 0x10 command.

I2C Interface Commands.

Devices with an I2C interface support hardware addressing. The device address is written into it during manufacturing, and when accessing the device, the adapter must first send this address.
Note. The least significant bit (LSB) of the I2C device address determines the transmission direction.
If the bit in the address byte is cleared, the subsequent bytes are written to the I2C device.
If the least significant bit in the address is set, data will be read from the device.
Technical descriptions of devices specify base addresses — with cleared least significant bits. They are always even.
This base address is what is used in computer commands and adapter responses.
Setting or clearing the least significant bit of the address is performed by the adapter when generating transmission sequences for the devices.
With single-byte addressing of the I2C interface, it is possible to generate 256 addresses, but since each device uses two addresses — one for reading and one for writing — the total number of addressable devices connected to the I2C bus cannot exceed 128.

Reading the State of I2C Device Registers.

Command:
0x11 addr_I2C Rg_minNum numRgToRead CR

Following the 0x11 command byte, the computer transmits:
the addr_I2C byte — the address of the polled I2C device,
the RgNum_min byte — the lowest register number from the sequence of polled registers,
the numRgToRead byte — the number of polled registers
and the CR byte — the control record.

Adapter response:
0x11 addr_I2C Rg_minNum B[0] ... B[numRgToRead-1] CR
the first 3 bytes are the same as in the command,
B[0] ... B[numRgToRead-1] — register states received by the adapter,
the CR byte — control record.
An example of the command and response is in the next section.

Writing to I2C Device Registers.

Command:
0x12 addr_I2C Rg_minNum B[0] ... B[n-1] CR
0x12 — command;
addr_I2C — address of the I2C device;
RgNum_min — the lowest register number from the register sequence to be written to;
B[0] ... B[n-1] — n bytes to be written to the registers;
CR — control record.

Adapter response: command echo.
An example of the command and response is in the next section.

SPI Interface Commands.

Unlike I2C devices, addressing when accessing SPI devices is not required.

Reading the State of SPI Device Registers.

Command:
0x21 Rg_minNum numRgToRead CR

0x21 — command to read register contents,
RgNum_min — the lowest register number from the sequence of polled registers,
numRgToRead — the number of polled registers
CR — control record.

Adapter response:
0x21 Rg_minNum B[0] ... B[numRgToRead-1] CR
первые 3 байта такие же, как в команде,
B ... B[numRgToRead-1] — states of the polled registers,
байт CR - control record.

Writing to SPI Device Registers.

Command:
0x22 Rg_minNum B ... B[n-1] CR
0x22 — command,
RgNum_min — the lowest register number from the sequence of registers to be written to,
B ... B[n-1] — n bytes to be written to the registers,
CR — control record.

Adapter response: command echo.

1-Wire Interface Commands.

Each manufactured device with a 1-Wire interface has an individual 64-bit address.
When a single device is connected to the adapter, addressless communication with it is possible.
Command:
0x31 n CR — read n bytes from the 1-Wire device buffer.
Adapter response:
B ... B[n-1] — bytes received by the adapter.

Command:
0x32 B[0] CR — send byte B[0] to the 1-Wire device.
No response is provided.

Command:
0x33 0x33 — the adapter generates a reset pulse for 1-Wire devices.
No response is provided.

Command:
0x34 0x34 — request the presence of devices on the 1-Wire line.
No response is provided.

DS18B20 Temperature Sensor: a dedicated command is provided for it in the program.
This command invokes all the 1-Wire interface commands listed above:
0x3F 0x3F — perform temperature measurement and transmit the measurement result.
Response:
9 bytes — the content of the DS18B20 buffer.
Bytes B and B contain the value measured by the DS18B20 sensor.
To get the result, use the formula:  T°C = (B + B * 256 ) / 16.

Example of addressing the DS18B20 sensor using individual 1-Wire commands:
0x33 0x33 — generate a device reset pulse.
0x34 0x34 — request the presence of devices on the 1-Wire line.
0x32 0xCC 0xFE — send byte 0xCC to the device. Command 0xCC of the DS18B20 sensor: SkipROM. 0xFE — control record byte.
0x32 0x44 0x76 — send 0x44 to the device. Command 0x44 of the DS18B20 sensor: measure temperature.
0x33 0x33 — generate a device reset pulse.
0x34 0x34 — request the presence of devices on the 1-Wire line.
0x32 0xCC 0xFE — send 0xCC to the device. Command 0xCC of the DS18B20 sensor: SkipROM.
0x32 0xBE 0xF0 — send 0xBE to the device. Command 0xBE of the DS18B20 sensor: ReadScratchPad — transfer memory content to the buffer.
0x31 0x09 0x3A — read 9 bytes from the buffer. The temperature measurement result is located in the first pair of buffer bytes of the DS18B20, but this buffer is circular; it contains 9 bytes and all these bytes must be read.

When executing the dedicated 0xFF command, the necessary delays are placed between some commands from the example. When manually entering each command into the computer application window, no delays are required.

 Application with Direct Access to CP2102N Functions

place a link to the archive containing the application and its source code



For the application to work, a direct access driver must be installed on the computer. The application works with adapters that have the USB bridge chip PID parameter set to 0xEA61.

The baud rate (500,000 baud), the number of data bits in the packet (8), the number of stop bits (1), and the parity bit (Odd) in this application and in the microcontroller program on the adapter board must be the same.

In the "Command (HEX codes)" window, the command is written as a sequence of hexadecimal codes separated by spaces;
symbols typically used in programming to denote hex formatting are not entered here — for example, instead of the code 0xE5, simply enter E5.
After pressing the "Send Command" button, the command is transmitted to the adapter and displayed in the "Command Sent:" window. If an adapter response is received within the time set in the "Rx Timeout, ms:" window, this response is displayed in the "Microcontroller Response:" window.
Response bytes that the computer does not manage to read within the set reception time are saved in the buffer (a reception time of 800ms is selected — slightly longer than the conversion time of the DS18B20 temperature sensor with a 1-Wire interface). When the next response arrives, the bytes saved in the buffer will be displayed in the window before that response. Additionally, the bytes remaining in the buffer can be read by pressing the "Read Again" button.
The adapter's microcontroller and the computer verify the integrity of the transmitted messages; to achieve this, each message byte is accompanied by a parity bit, and a control record (CR) is transmitted at the end of the message. The control record can be entered as a separate byte in the "Command (HEX codes)" window, or the command can be entered without the control record by checking the "+CR" checkbox — the control record will then be calculated automatically.
Here, the control record is a byte equal to the least significant byte of the sum of all command bytes; the control record byte is placed at the end of the command.
For example, for the last row in the "Microcontroller Response:" window, the control record is: LowByteOf (11 + 80 + E5 + 3F + B6) = LowByteOf (0x026B) = 0x6B.

The information exchange between the computer and the adapter is shown in the "Command Sent:" and "Microcontroller Response:" windows.
The following devices are connected to the adapter via the I2C interface: TMP117 temperature, LPS22HB pressure, and SHT21 humidity sensors; a DS18B20 temperature sensor is connected via the 1-Wire interface; an ADXL345 MEMS accelerometer is connected via the SPI interface (kit photo — the TMP117 sensor is missing from the photo).

First, Command 1
was transmitted: "10 a 0b aA BB 01 22 3 B0" — a connection test, to which the adapter responds with the exact same sequence (command echo).
10 — the 0x10 command byte, followed by an arbitrary sequence of bytes: a 0b aA BB 01 22 3, terminated by the control record byte B0.
When entering a command in the "Command (HEX codes)" window, you can use both uppercase and lowercase hexadecimal characters A...F.
If a byte value can be represented by a single character (for example, b), a leading zero can be added before it (0b).
The arbitrary sequence in the connection test command can be omitted.

Command 2 "10 10" — is also a connection test, containing only the command byte and the control record byte.

Command 3 "11 92 0 2 A5" — requests the result from the TMP117 temperature sensor:
command 0x11 — read register states of a device with an I2C interface
having the address 0x92 (the unique I2C address of the TMP117 temperature sensor),
start reading from register 0x00,
read 0x02 registers.
0xA5 — control record (will not be mentioned further).
Response: "11 92 00 0B DA 88" — the first 3 bytes of the command are repeated at the beginning so that the response can be interpreted (the device with address 0x92 was read, starting from register 0x00). The read result is placed between the 3rd and the last byte — in this response, the result is represented by 2 bytes.
The measurement result (the TMP117 transmits the MSB first, then the LSB) is 0x0BDA = 3034, which must be divided by 128:
T = 3034/128 = 23.703125°C.
 The calculation result is placed under the box with the formula (b3*256+b4)/128.
The result is valid only under the corresponding formula
either after receiving the adapter response when the "calculate results on microcontroller response" checkbox is checked,
or by double-clicking on a row in the "Microcontroller Response" window — the calculations will be performed specifically for this row, using all formulas.

Note: technical descriptions of devices connected to the adapter provide all necessary information:
device addresses, control register numbers, and registers containing measurement results,
operating algorithms — what, in which sequence, and into which registers of the device must be written to define the measurement mode and obtain the results.

Command 4 "12 BA 11 01 11 EF",
its purpose is to update the measurement result  in the registers of the LPS22 pressure sensor.
The transmission starts with byte 0x12 — this is a command to the adapter to perform a write operation to the registers of the connected I2C device;
followed by the I2C address of the device 0xBA — this is the address of the LPS22 pressure sensor,
into register 0x11 of which
0x01 byte must be written,
the value of this byte is 0x11.
The adapter's response to this command is an echo of the received sequence or an error code if errors are detected during command reception.
Results calculated under the formula boxes are invalid.

Command 5 "11 BA 28 03 F6" — read the measurement result from the LPS22 pressure sensor:
0x11 — reading register states; 0xBA — I2C address of the LPS22 sensor; starting from register 0x28, read the states of 0x03 registers.
Response: "11 BA 28 C3 44 3F 39". The first 3 bytes are the same as in the command; the next three bytes are the result, which the LPS22 transmits from the least significant byte to the most significant byte.
The sequence of data transmitted by the LPS22 C3 44 3F must be reordered to represent it in hex code: 0x003F44C3 = 4146371; to get the result in hectopascals, it must be divided by 4096 or shifted right by 12 bits; this gives 1012.2976 hPa.
The calculation result is placed under the box with the formula (b3+b4*256+b5*65536)/4096.

Command 6 "11 80 E5 02 78" — polling the SHT21 humidity sensor. 0x11 — read the register states of the device with I2C address 0x80, starting from register 0xE5, read 0x02 registers.
Response: "11 80 E5 3F B6 6B".  The first 3 bytes are the same as in the command. The result is 0x3FB6 — SHT21, just like TMP117, transmits the most significant byte first, then the least significant byte of the result: 0x3FB6 = 16310,
relative air humidity RH = -6 + 16310 * 125 / 65536 = -6 + 125 *16310/65536 = 25.1088%.
The calculation result is placed under the window with the formula -6+(b3*256+b4)*125/65536.

Command 7 "21 80 1 A2" — polling register 0x00 of the ADXL345 accelerometer chip via the SPI interface. 0x21 — read the register state of the device with an SPI interface; register number  0x00 (a feature of the ADXL345: when writing, the register number is transmitted unchanged; when reading a single register, 0x80 is added to the address; when reading a sequence of registers, 0xC0 is added), read 0x01 register.
Response: "21 80 E5 86".  The first 2 bytes are the same as in the command. The result 0xE5 is the single-byte identification code (ID) of the ADXL345 accelerometer, stored in its 0x00 register.

Command 8 "3F 3F" — addressing the DS18B20 temperature sensor with a 1-Wire interface.
Sensor response: "AF 01 4B 46 7F FF 01 10". Temperature is calculated using the 0th and 1st bytes (b0 and b1, respectively AF 01):
0x01AF / 16 = 431 /16 = 26.9375°C
The calculation result is placed under the box with the formula (b0+b1*256)/16 — only under this box in the picture is the up-to-date result, calculated for the last received response from the DS18B20 sensor.

As you can see, it is sufficient to use the adapter with the original firmware, connect any sensor to it, and, using the test application, debug the joint operation of the computer, adapter, and sensor.
You only need to find in the documentation of the connected device or sensor its unique I2C address or specific features of reading the SPI sensor, as well as the registers storing the result, the interpretation of these results, and, if necessary, what to write into which device register to start the measurement, change the mode, or update the result.

In the end, it all comes down to writing to the registers of the connected device and reading the states of its registers.

An already debugged series of commands can be selected and copied from the "Command Sent:" window and pasted into the "Notepad" window.
To copy a single command from the "Notepad" window into the "Command (HEX codes)" box, double-click on the row with the selected command in the "Notepad" window.

When the "Save" button is pressed, the set of commands from the "Notepad" window is saved to the Notes.st file. When starting the application, the last set of commands from this file will load automatically.
If you need to work with multiple command sets, save these sets into text files, and then paste them into the "Notepad" window or copy the Notes.st file.

After debugging the commands, you can adjust the test application, adapting it to the customer's requirements.
For example, you can hide unnecessary windows and fixed parameters for the project (baud rate, transmission mode, response timeout, etc.). Commands can be generated automatically without displaying them; you can add the necessary controls, organize an acceptable display of results, perhaps add a timer for periodic sensor polling, display charts of measured parameters, organize the saving and viewing of saved results, etc.

В окна расположенной внизу панели "Введите формулы ..." можно ввести до 4-х формул из технических описаний датчиков, тестируемых с адаптером.

Example.

The response of the LPS22 pressure sensor was discussed above:
11 BA 28 С3 44 3F 39, the byte numbering in this response is as follows:
B0 B1 B2 B3 B4 B5 B6.
The first three bytes are the same as in the request command, and the last byte is the control record. The response of the LPS22 sensor is contained in bytes B3, B4, and B5. According to the LPS22 technical description, these bytes are transmitted from least significant to most significant.
B5 is the most significant byte, it must be multiplied by 2^16 or 65536; byte B4 is the middle one, it is multiplied by 2^8 or 256; B3 is the least significant byte. The results must be summed up and divided by 4096. The formula for the calculation is written in the second box:
(B3+B4*256+B5*65536)/4096
To get the result in hectopascals, you need to double-click on the row with the LPS22 sensor response in the "Microcontroller Response" window. When the row is selected, one of its bytes is highlighted.
Calculations are performed for all entered formulas, but the correct parameter value will be displayed only under the corresponding formula. In the picture, the correct value of the parameter 1012.2976 is located under the formula for the LPS22 pressure sensor.

This option is intended for entering simple formulas similar to those discussed in the example.
